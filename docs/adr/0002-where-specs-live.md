# 0002 仕様と判断の置き場所を design.md、テスト、ADR、issue に分ける

## 背景

設計書に画面の細かい振る舞いと判断の理由まで書くと、UI を少し変えるたびに直す必要があり、更新が重くなる。

このリポジトリでは、AI と進める開発の運用を [yhiraki/ai-dev-template](https://github.com/yhiraki/ai-dev-template) から取り入れるときに、この決定もそのまま採用した。

## 決定

- `docs/design.md` には、目的、画面の大まかな構成、設定とアセットの扱い、API、認証、配備のような、めったに変わらない抽象的な内容だけを書く。
- 細かい振る舞いの原本はコードとテストとし、issue で決めた振る舞いは必ずテストで守る。
- 後の作業を縛る決定は ADR に、一つの issue の中で閉じる判断は issue に書く。

## 検討した案

- design.md を置かず issue だけで管理する案: 今の振る舞いを知るには関係する issue を全部読み、後の issue で覆された部分を差し引く必要があるので見送った。
- design.md に細かい振る舞いまで書き続ける案: 更新の重さが解消しないので見送った。

## 影響

- テストの無い振る舞いは原本が無いことになる。issue の完了の条件に、決めた振る舞いをテストで確かめる項目を必ず置く。
- 細かい振る舞いを知るにはテストを読む必要がある。
- この拡張は X のページで動くため、本物のタイムラインでの確認は自動化できない（ログインが要る）。X の DOM を模したページへの注入で確かめ、その手順を issue に残す（`docs/issues/0002` で照合のロジックをテストに出せたら、そこは自動で守れる）。
